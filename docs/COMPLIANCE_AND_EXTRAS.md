Документ для ревью: насколько реализация закрывает формулировки задания и что добавлено сверх минимума.

## 1. Сводка соответствия

| Область ТЗ | Статус | Комментарий |
|------------|--------|-------------|
| Стек: NestJS, Mongo, CH, Redis, Compose, React SPA | Выполнено | Frontend: React + Vite + TypeScript + Mantine + TanStack Query |
| CQRS: запись Mongo, аналитика CH, синк при мутациях | Выполнено | Sync-on-write + ретраи; аналитика через `AnalyticsService` → CH |
| 4 таблицы CH: users, promocodes, orders, promo_usages | Выполнено | Денормализация для человекочитаемых полей в аналитике |
| JWT, защита API, регистрация/логин | Выполнено | Access + refresh, глобальный guard + `@Public()` |
| CRUD пользователей/промокодов + деактивация | Выполнено | Mongo + синк в CH |
| Заказы: создание, свои заказы, отдельный apply-promocode | Выполнено | Валидация владельца, лимитов, дат, повторного применения |
| Redis ≥ 2 сценария | Выполнено | Кэш аналитики, lock, refresh-токены, rate limit |
| Таблицы на фронте: server-side page/sort/filter + даты | Выполнено | Страница аналитики, три таблицы, пресеты дат |
| Не загружать все строки на клиент | Выполнено | Параметры `page`, `pageSize`, сортировка на сервере |

Замечание по формулировке ТЗ (пример data flow с `GET /promocodes`): в проекте **список промокодов для управления (CRUD)** отдаётся из **Mongo** через API промокодов; **метрики по промокодам для аналитики** — из **ClickHouse** через `/api/analytics/promocodes`. Это согласуется с критерием «аналитические таблицы → CH» и с разделением command/query.

## 2. Критерии оценки из ТЗ (ориентир)

- **Запуск:** Compose с healthcheck, `.env.example`; возможны ручные шаги (отдельные терминалы backend/frontend) — зависит от интерпретации «всё из коробки одной командой».
- **CQRS / CH / синк:** закрыто; инвалидация кэша аналитики после мутаций улучшает согласованность с бонусом «кэш-менеджмент».
- **Backend:** DTO с class-validator, параметризованные запросы к CH, Redis по критериям.
- **Frontend:** три аналитические таблицы, пресеты дат, пагинация; формы с валидацией; уведомления об ошибках; защита маршрутов.
- **Бонусы:** Swagger и развитый набор unit-тестов в репозитории **могут отсутствовать** — см. README; приоритет был на основной чеклист.

## 3. Что сделано дополнительно и как влияет на работу

### 3.1. Устойчивость и эксплуатация

| Изменение | Влияние |
|-----------|---------|
| Ошибка инициализации ClickHouse при старте **не роняет** Nest | API (auth, CRUD Mongo) доступен, пока чинится CH; аналитика заработает после восстановления CH |
| Обработчик `error` у клиента **ioredis** | Меньше шума «Unhandled error event» в логах при сбоях Redis |
| Прокси Vite на **127.0.0.1:3000** | Снижает `ECONNREFUSED` из‑за IPv6 на Windows |
| README: том CH, пароль, Redis без publish порта | Быстрее диагностика типовых локальных проблем |

### 3.2. Кэш аналитики и инвалидация

- Ответы таблиц кладутся в Redis с коротким TTL; при создании/обновлении сущностей и заказах вызывается сброс кэша по префиксу `analytics:*`.
- **Плюс:** меньше нагрузки на CH при повторных одинаковых запросах.
- **Минус:** в течение TTL возможно устаревшее значение, если инвалидация не вызвана по какой-то ветке — при добавлении новых мутаций нужно не забывать `clearCache()`.

### 3.3. Конфигурация

- Joi-валидация env, загрузка `.env` из каталога backend и родительского (корень репозитория).
- Таймаут выбора сервера Mongo увеличен для дев-сценариев.

### 3.4. Health

- Модуль health с проверками зависимостей (в т.ч. Redis/CH) для мониторинга готовности.

## 4. Риски и честные пробелы

1. **Нет Swagger** — быстрее ручная проверка через фронт или HTTP-клиент.
2. **Unit-тесты** в объёме бонуса ТЗ не развёрнуты — регрессия вручную или e2e.
3. **Фильтрация по колонкам** на аналитике: реализованы ключевые фильтры (email, код, активность в DTO); не каждая колонка может иметь отдельный фильтр — уточнять по коду `AnalyticsTableQueryDto` и UI.
4. **Один compose** не поднимает Node-приложения — backend и frontend запускаются отдельно (часто приемлемо для тестовых заданий).
